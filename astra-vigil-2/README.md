# Astra Vigil 2.0

**Crew health console for long-duration missions. Holographic 3D, virtual reality, offline assistant.**
Team MANTA · NASA Space Apps Challenge 2026 · Author: Niloy Bhattacharjee · License: Apache-2.0

> ## ⚠ ALL TELEMETRY IS SIMULATED
> The four demo crew members are named after Team MANTA (**Niloy, Puja, Dhiraj, Tusar**) and use the team's photos, but their
> 600 days of vitals are **invented**: generated by
> `src/compute/fixture.py` with a fixed seed (`python3 tools/make_fixtures.py` rebuilds every file in `demo_fixtures/`). Nothing here is real astronaut data or anyone's real health data, and every number in
> the interface carries a **SIMULATED DATA** label. Astra Vigil is a research and demo project, **not a medical
> device**. It does not diagnose anything and gives no medical advice.

## What it does

A vitals stream replays one mission day per tick. The crew member is shown as a **real human astronaut**
(a photographic Apollo-style EVA suit with PBR textures), lit like a real object and then projected as a hologram. A **deterministic rule engine** compares each day with that
person's *own* 30-day baseline and raises an alert when a rule fires. The console then shows the rule, the exact
numbers behind it, a plain-language crew summary, and the cached NASA records (OSDR, NTRS, journal papers) that give
context. When an anomaly happens, the holographic astronaut flashes, a shockwave rings out, the chart marks the
moment, and the evidence drawer slides open.

**Nothing is diagnosed. Everything is evidenced.**

| Challenge requirement | Where it lives |
|---|---|
| 600-row simulated fixture with a planted anomaly | `demo_fixtures/vitals.json` (4 crew × 600 rows, one row per second of replay; demo beat = Niloy's HRV drop at index 250-251) |

## New in 2.4: crew photos, sound, Start flow, motion graphics

* **Crew and photos.** The four demo crew are **Niloy (Commander), Puja (Flight Engineer), Dhiraj (Medical Officer),
  Tusar (Mission Scientist)**. Portraits are read from the `crew_photos/` folder (`niloy.jpg`, `puja.jpg`, `dhiraj.jpg`, `tusar.jpg`).
  To change a face, replace that file (`.jpg` / `.png` / `.webp`, 3:4 portrait works best); no rebuild is needed, just reload
  the page. A crew member whose file is missing gets a generated helmet avatar.
  Photos show on the opening screen, crew rail, stage HUD, as 3D ID cards in VR, and as portraits on the 3D crew board.
* **Start, not Play.** The transport button reads **Start** (fresh) → **Pause** (running) → **Resume** (paused) →
  **Restart** (finished). The opening screen has **START MISSION** (unlocks sound and begins the replay) and "Look around first".
  In VR the **A** button does the same, and the 3D panel has the same START / PAUSE / RESUME / RESTART key.
* **Sound.** Every sound is synthesised in the browser with the Web Audio API: no audio files, no network. Button click and
  hover ticks, start / pause / resume cues, an alert klaxon, an evidence chime, an "arrived on Earth" ping, a soft station
  ambience. The speaker button and volume slider are in the top bar; the choice is remembered. Browsers only allow sound
  after a click, which is why the opening screen asks for one.
* **Motion graphics and buttons.** Warp-speed star field, rotating HUD rings, animated title, tilting crew cards with scan
  line, status rings around portraits, and a layered glass button system with sheen, press-in, ripple and SVG icons. 3D keys
  in the spatial view and VR lift on hover and sink when pressed. `prefers-reduced-motion` switches the animation off.
* **3D design.** A procedural orbital station (spinning habitat ring, hub, truss and solar wings) sits behind the astronaut
  on the desktop view; in VR a wall of four floating crew ID cards faces the viewer (click one to select that crew member).

## Run it (offline, no internet needed)

Needs Python 3.10+. The built frontend is already included in `backend/astra/static`.

```bash
./start.sh            # Linux / macOS     (start.bat on Windows)
# or
pip install -r requirements.txt
python run.py --open  # http://localhost:8000
```

Press **START MISSION** on the opening screen (or **Start** in the transport bar), then click **Rehearse demo beat**: it jumps to four days before the planted HRV event and plays at ×1. About five seconds
later the alert fires.

**Rehearsal tab** (right panel): a true one-sample-per-second simulated stream with the anomaly planted at index 420.
Press *Jump to 10 s before*, pick a replay speed, and watch the baseline band, the alert at index 420 and the cited
record appear. *Clean twin* replays the same noise with nothing planted: no alert should fire. The same data is
available without the browser: `GET /api/rehearsal/alerts` (batch run), `GET /api/rehearsal-fixture` (raw samples),
`ws://127.0.0.1:8000/ws/rehearsal?speed=20&start=410`. The rehearsal stream is a demo fixture, not a crew member, so
it sits outside the crew privacy tiers. Study metadata stays available offline at `/api/evidence`.

Replay a different fixture with `ASTRA_VITALS=vitals_clean.json python run.py` (`ASTRA_FIXTURES` points at another
folder). Every fixture is checked against `src/compute/schema.py` when it is loaded; a file that is malformed or not
marked `simulated: true` is refused.

To rebuild the frontend (only if you change it): `cd frontend && npm ci && npm run build`.
The build writes into `backend/astra/static`.

## The detection rules

Six signals: resting heart rate, HRV, SpO2, sleep duration, core temperature, exercise minutes.
The baseline is the person's own last 30 days (at least 14 needed). Days inside a *confirmed* episode are left out of
the baseline, so a long event cannot quietly become the new normal.

* **Rule S (single signal):** one signal is ≥ 2.0 SD in its worse direction for 2 days in a row.
* **Rule M (multi signal):** two or more signals are ≥ 2.5 SD worse within a 2-day (48 h) window.
* In the 1 Hz rehearsal stream the same two rules run with `Config.per_second()` (90-sample baseline, 2.5 / 3.0 SD,
  3-sample persistence, 5-sample window), because a second-resolution signal needs a longer memory than a daily one.
* **Status:** `learning` → `normal` → `watch` (one signal past threshold) → `alert` (a rule fired, held 3 days).

Every alert carries the rule name and, per signal: current value, baseline mean and SD, z-score, threshold, window.
No interpretation. All thresholds are in `Config` and can be changed.

Simulated scoreboard (Monte Carlo, 400 runs per scenario, `tools/montecarlo.py`): single planted HRV event caught
99.8% (mean delay 0.98 day); three-signal event caught 98.0%; about 24 chance alerts per 1000 crew-days (so an ordinary noisy 600-day run is **not** alert-free; the clean fixture is
quiet by construction and says so). These
numbers describe the detector on **simulated** noise only. They are not a clinical performance claim.

## Roles and privacy tiers

The server filters what each role receives. The browser never gets numbers its role may not see.

| Tier | Who | Sees |
|---|---|---|
| 0 | the crew member | own raw numbers, baseline, alerts, explanations |
| 1 | medical designee, **with the crew member's consent** | trend direction only ("steady", "drifting toward worse") |
| 2 | commander, Earth (ground) | a status word only. Earth receives it through the **outbox, after the one-way light-time delay** |

The outbox allow-list has no numeric vitals fields. Delay presets: Moon 0.02 min, Mars 3.04 / 12.51 / 22.29 min. In the
demo, 1 modeled minute = 1 second, and you can watch the packets travel to Earth in the 3D scene.
Every alert, status change, consent change and control action goes into a **hash-chained audit log** (SQLite).
Editing or deleting a row breaks the chain; the Trust tab verifies it.

> The role selector is a demo control, **not authentication**. A real deployment needs real identity and device
> binding.

## Explanation agent and offline assistant

**Explanation agent** (`backend/astra/agent.py`). Detection is code; the agent only describes what the rule found. It
receives *one* alert object plus cached NASA records, passed through a whitelist (no crew name, no raw series, no
ground-truth label, no user question). It must cite a record by id; **the URL is attached by code from the cache, never
taken from model text**. Two layers keep it from diagnosing:

1. `SYSTEM_PROMPT` tells it to describe deviation only, use only numbers from the alert, cite supplied ids, and never
   diagnose, predict, advise or interpret.
2. `post_check` rejects the answer if it has diagnostic or treatment language (`compute/guard.py`), words of
   interpretation, cause, prediction or advice, any number not in the alert, any record id or URL not supplied, or no
   valid citation. A rejected answer is replaced by a deterministic template and the reasons go to the alert's
   `explanation_blocked` field.

With no model configured (the default) the template **is** the agent, so everything works offline. To use a local model
set `ASTRA_OLLAMA_MODEL=<model>` (Ollama on localhost); the model's text still has to pass the post-check. This path is
tested with a stub model; it has not been run against a real model in this build.

**Offline assistant** (`backend/astra/assistant.py`). Answers *what changed*, *which rule fired*, *the numbers*, *which
cached NASA records are linked*, *who can see my data*, *is this real data*, in English and Bangla. Rule-based, runs
from tool results only, and every sentence passes the same guard. Questions about health meaning, treatment or
"should I…" get a fixed boundary reply that sends the person to the flight surgeon. The reference design's
medical-advice panel is intentionally **not** implemented.

## NASA OSDR metadata cache

`tools/cache_osdr.py` refreshes the OSDR records in `evidence_cache.json` from the OSDR Biological Data API
(`visualization.osdr.nasa.gov/biodata/api/v2/dataset/OSD-xxx/`), keeps the hand-curated signal→study `mappings`, and
re-validates the file (`Evidence.validate()`: https URLs, ids match URLs, every mapping points at a real record). A
failed fetch keeps the old record and exits non-zero. `--validate` checks the cache offline. The app itself never calls
the network.

```bash
python3 tools/cache_osdr.py --validate          # offline
python3 tools/cache_osdr.py                     # refresh all OSDR records (needs internet)
python3 tools/cache_osdr.py --add OSD-123       # add a study, then add its mapping by hand
```

## Virtual reality

Press **Enter VR**. You stand in a round **mission-control cabin** (wall panels, three observation windows, one facing
Earth, floor status strip that turns red during an alert). The astronaut stands life-size on a hologram pedestal 2.2 m in
front of you, with panels placed around you: crew status, detection alert + NASA evidence, a 3D chart with the baseline
band, the **offline assistant** (tap a question, read the answer), a controller cheat-sheet, and playback controls.

| Input | Action |
|---|---|
| Left stick | walk around the cabin (stops at the pedestal and the wall) |
| Right stick left/right | snap-turn 30° |
| Trigger / pinch on a button or a glowing dot | press it; a dot changes the chart signal |
| A / B | start-pause / rehearse the demo beat |
| X / Y | hologram-realistic look / back to start |
| Panel buttons | TURN < >, SIZE LIFE/DESK (a half-size hologram at waist height), LOOK |

Both controllers give a short haptic pulse when an alert fires.

* **Headset (Meta Quest Browser or any WebXR browser):** open the page over `https` or `localhost`. For a Quest on USB:
  `adb reverse tcp:8000 tcp:8000`, then open `http://localhost:8000` in the headset browser and press **Enter VR**.
* **No headset:** **Enter VR (emulated)** starts a Meta Quest 3 emulator (IWER) inside the page.
* **Spatial view:** the same 3D panels on a normal screen (drag to orbit, click buttons).

3D text is English only (the 3D text engine cannot shape Bangla); the 2D dashboard is fully bilingual.
Hand tracking works as a pointer (point and pinch); hands are not drawn as 3D models, because the stock hand model is
loaded from a CDN and this app never touches the network.

## Offline guarantee

No CDN, no web fonts, no downloaded textures or models. Fonts are bundled (`@fontsource`), the astronaut model is
bundled (`frontend/public/models/astronaut.glb`), Earth, stars, platform and the VR cabin are procedural shaders, reflections come from
local light panels (no HDR download), and VR controller models are served from `frontend/public/xr-profiles`.
The browser test (`tests/e2e/smoke.mjs`) fails if any request leaves localhost.

## Honest limits

* Simulated data only; the detector has never seen a real astronaut. Its thresholds are illustrative.
* Mapping a signal to NASA records is a *context pointer*, not proof that a rule is clinically meaningful.
  The evidence cache was fetched on 2026-10-20; it is not refreshed automatically. `tools/cache_osdr.py` is tested
  against a stubbed API response only: the build sandbox could not reach NASA hosts, so a live refresh was not run here.
* The clean fixture has zero alerts because its noise is bounded by construction. Ordinary Gaussian noise gives about 24
  chance alerts per 1000 crew-days, and the published scoreboard says so.
* The local-model path of the explanation agent is tested with a stub, not a real model.
* VR was tested with the IWER Quest 3 emulator (thumbstick walking, snap-turn, panels, assistant), **not on a physical headset**.
  Frame rate on real hardware is unmeasured; the 3D astronaut uses 2K textures (1K for the lighting maps) and the cabin is pure shader work.
* The astronaut model is a **third-party asset** (see `CREDITS.md`); confirm its licence before you publish the project publicly.
* Prediction is not implemented. Detection only.
